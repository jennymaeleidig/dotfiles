# Hashline owns the edit surface

`npm:pi-hashline-edit-pro` is declared in the pi settings. It is not an additive extension: on `session_start` it registers its own `read`, disables the built-in `edit`, and disables `grep` in favour of its `anchor_grep`. Every line it serves is prefixed with a session-scoped anchor, and an edit against a superseded or ambiguous anchor is refused rather than fuzzy-matched — which is precisely the failure mode (wrong-location edits escalating into full-file rewrites) that motivated adopting it. The override is therefore the feature, not a cost to be mitigated, and the package is left unpinned like every other entry in `packages`; its config is pinned instead. `dot_config/pi-hashline-edit-pro/config.json` carries only the toggles that change **which tools exist** — `anchorGrepEnabled`, `copyMoveEnabled`, `replaceMatchEnabled`, `autoReadAll` — so an upstream default flip cannot silently re-enable the built-in `grep`. The extension rewrites that file when a toggle is changed from `/hashline-config`, so Source state is the truth: a UI toggle is reverted by the next Apply unless it is added back to Source. The package needs Node ≥22.19 for `node:sqlite`; the pnpm launcher already runs pi under Node rather than its bundled Bun.

`dot_pi/agent/extensions/find-dedup.ts` is the one piece of glue. `@ff-labs/pi-fff`'s `override` mode is all-or-nothing — it takes `grep`, `find`, and `multi_grep` together — so running it in override would race hashline for the `grep` name, with the winner decided by undocumented `session_start` ordering. Instead pi-fff stays in its default mode, where it registers `fffind` beside the built-in `find`, and the glue drops the built-in `find` on `before_agent_start` whenever `fffind` is present. The prune is conditional so that removing pi-fff, or switching it to override, leaves a working finder rather than none.

Nothing in `~/.pi/agent` currently assumes line-numbered `read` output or the presence of the built-in `edit`/`grep`, so the blast radius is contained to what the model sees in a session.

Considered options: pi-fff `override` mode plus a shim to arbitrate the `grep` race (rejected — would depend on extension load order, which neither package documents); forking pi-fff to add a per-tool override (rejected — ongoing maintenance for a cosmetic gain); leaving both finders active (rejected once the pruner was judged cheaper than the occasional wrong-tool call); and declining the package entirely (rejected — the re-read and wrong-edit cost it targets is real).
