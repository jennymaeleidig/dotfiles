# Pi packages are declared in settings and materialized as runtime state

The pi app config is managed declaratively: the `packages` array in the pi settings dotfile names each package, and pi fetches and materializes them into runtime state (`~/.pi/agent/npm/` and `~/.pi/agent/git/`) on startup — the same split as opencode, where plugins were listed in the config while `node_modules` stayed runtime. Considered options: imperative `pi install` steps at provision time (rejected — packages would be invisible to Source state and unreproducible on a fresh host) and chezmoi-managing the materialized package trees (rejected — they are runtime state by definition). Consequences: `pi install` is a bootstrap-only action, the settings dotfile is hand-managed thereafter, and Apply must never touch the `npm/` or `git/` trees.

## Update (2026-08-15): verify peer ranges before declaring

A package that does not support the running pi version can break interactive startup silently: `npm:pi-tool-display@0.5.0` (peers `pi-coding-agent ^0.74–^0.80`) made pi 0.84.1 exit 1 with zero output before the TUI drew — diagnosed by bisecting: `pi -ne` launched, and removing the package from settings restored startup. Extension load failures on the interactive path are not printed when the offending import throws during registration. Rule: check the candidate's `peerDependencies` against the installed version before adding it to the settings dotfile; a package outside the peer range lands in `packages` only after a `pi install` smoke test that ends with an interactive launch. `pi-tool-display` was removed again; re-add when upstream extends its peer range.
