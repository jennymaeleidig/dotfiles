# Themes are dependencies, not vendored copies

Theme files were copied into each app's config directory (ghostty, opencode, bat) with a `tools/themes/README.md` instructing to keep the copies in sync. They are now kept as chezmoi externals: the ghostty (`Kirlovon/monokai-ghostty`), opencode (`monokai-pro/opencode`), and pi (`krfantasy/pi-monokai-pro`) themes are fetched from their upstream repos by Apply into exactly the flat file paths those apps require (ghostty resolves themes only as flat files in `themes/`, opencode scans `themes/*.json` one level deep, pi discovers custom themes from `~/.pi/agent/themes/*.json`), with a 168h refresh period so upstream changes land on periodic refreshes. The user-created shiki and bat themes stay as plain files — `tools/themes/monokai-pro.json` (consumed by an obsidian plugin reading from the iCloud vault, which is outside the source tree) and `dot_config/bat/themes/Monokai Pro.tmTheme` (already at its consumer path) — until they are published to their own repos, at which point each becomes an external with a `file://`-free URL.

Considered options: git submodules (rejected — submodules mount a directory, so the theme file sits one level deeper than the flat path ghostty, opencode, and pi require, forcing symlink dotfiles), local-path `file://` externals for the user-created themes (rejected — circular for in-source-tree consumers, and they break fresh-host provisioning since the path only exists on this machine), and keeping copies (rejected — sync burden without a single source of truth). `tools/themes/README.md` was deleted; `.chezmoiexternals.toml` is now the theme inventory and the external targets are gitignored since Apply materializes them.
