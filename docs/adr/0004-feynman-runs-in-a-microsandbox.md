# Feynman runs in a microsandbox

Feynman is a research agent that runs tools, fetches sources, and writes artifacts on the host's behalf — exactly the workload microsandbox's microVMs exist to fence. We therefore route every `feynman` invocation through `msb run` instead of letting the binary touch the host directly. The shell function in `dot_bash_aliases` dispatches to `msb run --conf ~/.config/feynman/sandbox.yaml`, and the msb config (a Template rendering to `~/.config/feynman/sandbox.yaml`) owns the image, resources, mounts, network policy, and the `feynman serve` port forward.

Two constraints shaped the config. The host feynman bundle is darwin-arm64 and cannot execute inside the Linux guest, so `feynman-vm-setup` (a Script at `~/.local/bin/feynman-vm-setup`) downloads the linux-arm64 release bundle, verifies it against the release's SHA256SUMS, and extracts it into an msb **disk volume** named `feynman` (raw ext4, virtio-blk — guest-native speed) via a one-off builder sandbox; a relative `current` symlink inside the volume is what the guest wrapper execs, so version bumps re-run the setup script and never touch the sandbox config. The volume is a disk rather than a host bind mount because feynman's first boot extracts a bundled 61 MB / 23k-file workspace into its app dir and hashes it on every start — unbearable over virtiofs, fast on ext4, and the volume persists the workspace and package installs across ephemeral `msb run` boots. Feynman's user-level state must also survive across the VM boundary: `~/.feynman` (auth, sessions) and `~/.ahub` (alphaXiv auth) are bind-mounted in, so model login done on either side works in both. Provider API keys should use msb secrets (per-domain injection) rather than plain env passthrough.

One more trap shaped the ports config: msb publishes host ports by dialing the guest's eth0 IP through a smoltcp netstack, but feynman binds its servers (the workbench and the alphaXiv OAuth loopback callback) to 127.0.0.1 inside the guest, so direct host-to-guest forwards get connection-refused. A tiny node TCP relay (written by a rootfs patch at boot, started by the guest wrapper) exposes those loopback services on 0.0.0.0, and the ports block maps host ports to the relay instead. Pi extensions are bundled declaratively: the canonical list lives in `feynman-vm-setup` (`EXTENSIONS`), which merges it — plus any declared pi settings keys (`SETTINGS_BLOB`, e.g. pi-compact-transcript's recommended `hideThinkingBlock`/`outputPad`) — into `~/.feynman/agent/settings.json` (feynman's pi home, mounted into the VM) on every run — pi materializes them from npm into the VM workspace at startup, so the declaration survives volume rebuilds while the materialized tree rides the volume. Peer ranges are checked against the bundled pi version per docs/adr/0004.

**Consequences**: `feynman` needs msb to boot a VM (first boot pulls the debian image; macOS prompts for file access when mounting host paths). The native feynman install becomes optional once the volume is populated — the escape hatch is `FEYNMAN_NATIVE=1 feynman ...` and uninstalls cleanly (remove `~/.local/bin/feynman` and the `~/.local/share/feynman` bundle; keep `~/.feynman`, it is the shared auth/state). Research sessions needing the working directory run outside `$HOME` so the wrapper can mount only that directory (symlink-resolved via `pwd -P`) at `/workspace` — mounting all of `$HOME` would gut the sandbox boundary. The disk volume is not concurrency-safe: two simultaneous `feynman` VMs would rw-mount the same ext4 image, so treat feynman as single-instance. The guest feynman version is whatever `feynman-vm-setup` last installed; upgrading means re-running it, which rebuilds the volume (in-VM package installs are lost with it).

## Update (2026-09-08): guest config is declared in Source state and rendered

The canonical `EXTENSIONS` list and `SETTINGS_BLOB` no longer live in `feynman-vm-setup`. Shared pi preferences and the guest extension list are declared once in `.chezmoidata/pi-prefs.toml` and rendered into two adapters: the host pi settings (`dot_pi/agent/settings.json.tmpl`, shared + host-only keys) and the guest pi declaration (`dot_config/feynman/pi-guest-prefs.json.tmpl`, shared keys + packages, applied to `~/.config/feynman/pi-guest-prefs.json`). The pi config concerns split out of `feynman-vm-setup` into `feynman-pi-sync` (a Script that merges the guest declaration into `~/.feynman/agent/settings.json` and overlays keybindings, called on every launch by the `feynman` shell function); `feynman-vm-setup` now owns only Guest bundle provisioning (download, verify, volume build) and invokes the sync at the end. The relay and guest entrypoint are real source files (`dot_config/feynman/relay.js.tmpl`, `dot_config/feynman/guest-feynman.sh`) rendered into the sandbox config, with the port pairs single-sourced in `.chezmoidata/feynman-sandbox.toml` instead of duplicated between the relay and the `ports:` list.
