# Feynman runs in a microsandbox

Feynman is a research agent that runs tools, fetches sources, and writes artifacts on the host's behalf — exactly the workload microsandbox's microVMs exist to fence. We therefore route every `feynman` invocation through `msb run` instead of letting the binary touch the host directly. The shell function in `dot_bash_aliases` dispatches to `msb run --conf ~/.config/feynman/sandbox.yaml`, and the msb config (a Template rendering to `~/.config/feynman/sandbox.yaml`) owns the image, resources, mounts, network policy, and the `feynman serve` port forward.

Two constraints shaped the config. The host feynman bundle is darwin-arm64 and cannot execute inside the Linux guest, so `feynman-vm-setup` (a Script at `~/.local/bin/feynman-vm-setup`) downloads the linux-arm64 release bundle into `~/.local/share/feynman-vm`, verifies it against the release's SHA256SUMS, and maintains a `current` symlink the guest wrapper execs — version bumps never require an msb config change. And Feynman's state must survive across the VM boundary: `~/.feynman` (auth, sessions, packages) and `~/.ahub` (alphaXiv auth) are bind-mounted in, so model login done on either side works in both. The mount is read-only for the bundle but read-write for state; provider API keys should use msb secrets (per-domain injection) rather than plain env passthrough.

**Consequences**: `feynman` needs msb to boot a VM (first boot pulls the debian image; macOS prompts for file access when mounting host paths). Host-native escape hatch is `FEYNMAN_NATIVE=1 feynman ...` for maintenance like the bundle installer itself. Research sessions needing the working directory run outside `$HOME` so the wrapper can mount only that directory at `/workspace` — mounting all of `$HOME` would gut the sandbox boundary. The guest `feynman` version is whatever `feynman-vm-setup` last installed, and can drift from the host bundle; refresh both together when upgrading.
