# Slash prompts are mermaid state diagrams that dispatch ralph-runner subagents

A slash prompt (`/name` in `dot_pi/agent/prompts/`) is written as a small state machine, not a one-shot instruction: its body is one fenced Mermaid `flowchart TD` diagram with explicit transitions and one terminal "report back" state, wrapped in a single subgraph that names the prompt's one `ralph-runner` loop; `description` and `argument-hint` stay in frontmatter and a fixed run preamble is the only prose. This ADR records **why** prompts are machines; **what** the shape is lives in `dot_pi/CODING_STANDARDS.md` (prompt file format) and the shared vocabulary in `dot_pi/CONTEXT.md` (`Prompt file` / `Prompt state machine` / `Prompt lifecycle`).

A prompt is a machine so a run is verifiable and resumable: substantive work dispatches to an isolated `ralph-runner` subagent, orchestration (pick next ticket, branch, report back) runs inline, and every run ends at the report state — a prompt that never reaches it hands the human nothing. The user invokes the prompt at a single point of the lifecycle and runs only its internal machine, not the lifecycle.

Two exceptions shape the machine:

- `/wayfind` is the ONE prompt not a ralph-runner loop — it is interactive, wrapping the `wayfinder` skill with the human in the loop: no `[[ ]]` dispatch, no `ralph-runner` subagents, no loop subgraph. The deviation stays sanctioned because the prompt itself is a conversational map-charting workflow; do not reuse it for any other prompt.
- `implement` is a sub-state-machine with one entry — automated (`/implement-effort` drives the whole frontier, cycling `implement-ticket` → `close-ticket`, then `close-effort`). Its per-ticket question-bubbling (seam design, review gaps, closure blockers) is the supervision gate, so a separate supervised per-ticket prompt path (`/implement-ticket` → `/close-ticket`) was removed as redundant — it re-exposed the same machines the loop already gates. The per-ticket workflows remain: they are the machines `/implement-effort` composes, not user-facing states. _(Amended: the two-mode entry was superseded when `/implement-ticket` and `/close-ticket` prompts were retired.)_

Considered options: prompts as free-form instructions (rejected — no verifiability or resumability, no consistent delegation, so a half-run prompt leaves nothing checkable); prompts as prose numbered steps with the diagram only implied (replaced — two sources of truth, so prose and transitions drift); dispatching nested loops inline (rejected — nested loops run in the parent context, clouding it and defeating the isolation `ralph-runner` exists for; the `subagents` skill requires delegation). Consequences: every prompt must end on a report state; a work state that forgets to dispatch runs heavy work in the prompt loop; an edit must preserve the diagram and node-shape language or the prompt stops reading as a machine. Dispatch is enforced, not just instructed: the run preamble (copied verbatim across all prompts) mandates one foreground `ralph-runner` subagent as the prompt's only entry, and the wrapper's fixed `ralph_start` defaults (`maxIterations: 20`, `reflectEvery: 5`) act as a fingerprint; `ralph-runner` runs with `thinking: high` because the completion gate is a rush-risky judgment.
