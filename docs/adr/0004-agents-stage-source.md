# Agents stage source; the user applies

> **Superseded in part by [ADR-0009](0009-the-os-fence-is-removed.md).** The OS fence this mechanism relied on is removed. The stage-source / user-applies split below now holds as repo policy, not as an enforced boundary.

The guard's `allowWrite` covers the source repo, `~/.pi/agent/sessions`, `~/.pi/agent/agent-memory`, `/tmp`, `~/.npm`, and the OS temp directory — deliberately not `~/.zshrc`, `~/.config/**`, or `~/Library/**`, which is where much of the source lands. An agent-run `chezmoi apply` therefore cannot complete: those writes hit the fence as `EPERM` or a refusal. The denial starts earlier than the write, though — `denyRead` covers the home root and `allowRead` re-allows named roots (the repo, `~/.local`, `~/.config`, `~/Library`, `~/.pi`, and a handful of tool directories) but not the home root itself, so **any command that inspects target state fails on the first `lstat` of a home-root file**: `chezmoi apply`, `chezmoi diff`, and `chezmoi status` all stop at `~/.aerospace.toml` with `operation not permitted`, dry run or not. Widening `allowWrite` to every apply target would hand an agent write access across the whole home directory, which is the one thing the fence exists to prevent; removing the sandbox would leave no OS-level enforcement at all, and no tool-layer guard can replace it. So the boundary stays narrow and the division of labour is: **the agent works from source; the user applies it.**

Each guard keeps one job. `pi-sandbox-runtime` enforces at the OS level, including subprocesses and argv, and is an allow-list: anything outside `allowWrite` is denied. `cc-safety-net` blocks known-bad commands at the tool layer.

Consequences: an agent never runs `chezmoi apply`, `diff`, or `status`. Source-side commands work and are the agent's tools for showing what a change would do — `chezmoi managed`, `chezmoi target-path`, `chezmoi source-path`, and `chezmoi execute-template` (templates read from the source tree, so a rendered result can be inspected without touching a host). To verify an applied change, the agent asks the user to apply and then reads the target directly when it sits under an `allowRead` root (`~/.config`, `~/.local`, `~/Library`, `~/.pi`); home-root dotfiles such as `~/.zshrc` are not readable at all, so those results come from the user. Any future guard configuration is read as what it adds beyond the sandbox built-ins, not as a restatement of them. The guard itself changed after this decision — from `carderne/pi-sandbox` to `pi-sandbox-runtime` — see ADR-0006.
