# Agents stage source; the user applies

The sandbox's `allowWrite` covers the source repo, `~/.pi/agent/sessions`, `~/.pi/agent/agent-memory`, `/tmp`, `~/.npm`, and the OS temp directory — deliberately not `~/.zshrc`, `~/.config/**`, or `~/Library/**`, which is where much of the source lands. An agent-run `chezmoi apply` therefore cannot complete: those writes hit the fence as `EPERM` or a prompt. The denial starts earlier than the write, though — `allowRead` names specific roots (the repo, `~/.local`, `~/.config`, `~/Library`, `~/.pi`, and a handful of tool directories) and not the home root, so **any command that inspects target state fails on the first `lstat` of a home-root file**: `chezmoi apply`, `chezmoi diff`, and `chezmoi status` all stop at `~/.aerospace.toml` with `operation not permitted`, dry run or not. Widening `allowWrite` to every apply target would hand an agent write access across the whole home directory, which is the one thing the fence exists to prevent; removing the sandbox would leave no OS-level enforcement at all, and no tool-layer guard can replace it (a command-pattern guard and warden's path rules never classify paths in arbitrary argv, so a script or `cp` writing anywhere is invisible to both). So the boundary stays narrow and the division of labour is: **the agent works from source; the user applies it.**

Each guard keeps one job. `pi-sandbox` enforces at the OS level, including subprocesses and argv, and is an allow-list: anything outside `allowWrite` is denied. `cc-safety-net` blocks known-bad commands at the tool layer. `pi-warden` judges context and advises; its action guard already holds a write that overwrites an existing file outside the project, and it warns on touches of credentials files through its built-in `sensitive-path` pattern. Warden's `pathRules` are deliberately **not** used to mirror the sandbox's allow-list: a deny-list cannot cover more than an allow-list already denies, and mirroring it would mean maintaining the same policy in two places. The only path rule kept is one that protects configuration no other layer covers — the guards' own config under `~/.pi/agent/pi-warden/`, `~/.pi/agent/sandbox.json`, and `~/.cc-safety-net/` — which matters on sessions that run outside the fence (a Herdr pane started by the server, `pi --no-sandbox`, `/sandbox-disable`), where warden still runs and the sandbox does not.

Consequences: an agent never runs `chezmoi apply`, `diff`, or `status`. Source-side commands work and are the agent's tools for showing what a change would do — `chezmoi managed`, `chezmoi target-path`, `chezmoi source-path`, and `chezmoi execute-template` (templates read from the source tree, so a rendered result can be inspected without touching a host). To verify an applied change, the agent asks the user to apply and then reads the target directly when it sits under an `allowRead` root (`~/.config`, `~/.local`, `~/Library`, `~/.pi`); home-root dotfiles such as `~/.zshrc` are not readable at all, so those results come from the user. Any future guard configuration is read as what it adds beyond the sandbox and warden's built-ins, not as a restatement of them.
