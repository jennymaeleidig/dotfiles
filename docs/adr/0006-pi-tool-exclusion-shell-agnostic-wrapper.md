# Pi raw-builtin exclusion is a shell-agnostic PATH wrapper

pi's `--exclude-tools bash,read,ls,hypa_grep,hypa_find` flag (drop raw builtins so the model uses hypa/fff replacements) is CLI-only — pi 0.84.1 exposes no settings.json key and no environment variable for tool exclusion. An `alias pi='command pi --exclude-tools ...'` in `dot_bash_aliases` confined the exclusion to interactive bash: zsh terminals, VS Code integrated terminals (whose default shell may be zsh, and no `terminal.integrated.defaultProfile` is configured), and GUI shell launchers all resolved the raw binary and ran with the builtins exposed.

The exclusion now lives in a wrapper script at `~/.local/bin/pi` — materialized by the hashed-content onchange script `.chezmoiscripts/run_onchange_write-pi-wrapper.sh.tmpl` — which `exec`s the real binary (`/opt/homebrew/bin/pi`) with the flag list appended. Every launch through `PATH` inherits the exclusion regardless of shell: interactive bash already puts `~/.local/bin` before `/opt/homebrew/bin` (`dot_bashrc:11`), the newly managed `dot_zshrc` adds the same `~/.local/bin` PATH entry for zsh (preserving the unmanaged ghcup line), and the VS Code pi-launcher extension's `sendText("pi")` resolves through PATH too. The bash alias was deleted — the wrapper is the single source of truth for the exclusion list.

The wrapper is an onchange script rather than a plain dotfile because chezmoi strips the executable bit from regular files (verified: a 755 source applies as 644), and a non-executable wrapper silently fails at every `pi` launch. The script's own content embeds the wrapper text, so editing it changes the script content and triggers re-run via chezmoi's content-hash mechanism (ADR 0001) — the exec bit self-heals on the next apply.

**Consequences**: any change to the exclusion list means editing the wrapper text inside the script, not an alias; the wrapper hardcodes `/opt/homebrew/bin/pi` and must be updated if pi moves from Homebrew to mise (whose shims precede `~/.local/bin` in `dot_bashrc:4`); and `~/.local/bin/pi` is runtime state written by Apply — dropping it on a fresh host requires one apply to materialize it.

## Update (2026-08-15): subcommands bypass the exclusion

The exclusion is injected for session launches only. pi dispatches its one-shot commands (`install`, `remove`, `uninstall`, `update`, `list`, `config`, `auth`) by `args[0]` in `parsePackageCommand` (`dist/package-manager-cli.js`), so an unconditional leading `--exclude-tools` made pi miss the command and treat `install npm:…` as a chat prompt: TTY launches opened the TUI/file-picker instead of installing, and home-directory cwds surfaced `FFF init failed: … Can not run certain FFF features in a file system root or home directories`. The wrapper now switches on `"${1:-}"` and omits the flag for the subcommand set; every interactive and `--print` launch keeps the exclusion. `npm:pi-tool-display` install failed for this reason before the fix.
