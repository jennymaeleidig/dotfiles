# The sandbox guard is pi-sandbox-runtime

> **Historical.** The guard this records has been removed; it is no longer current configuration.

The OS-level boundary is `git:github.com/jennymaeleidig/pi-sandbox-runtime`, which drives [`@anthropic-ai/sandbox-runtime`](https://github.com/anthropic-experimental/sandbox-runtime) directly, in place of `carderne/pi-sandbox` v0.6.8. The older extension fenced `bash` only: `grep`, `find` and `ls` ran unchecked against the whole filesystem, and a Tool contributed by another package — a formatter that rewrites files in place is neither `write` nor `edit` — was never judged. The replacement judges every Tool call before it runs and fences shell commands through the same runtime, so one policy governs both. It is stricter on the axes that mattered: Tool coverage, and a fail-closed policy where an unrecognised config key is a load error and a Tool whose paths cannot be determined is refused rather than allowed. It also trades the predecessor's interactive write prompt for in-memory session grants (`/guard-allow`), so nothing the agent opens becomes file state nobody remembers granting.

Three behavioural differences from the mechanism ADR-0004 originally recorded are load-bearing. Reads are **default-open** outside `denyRead` (the home root by default), with `allowRead` re-allowing named roots beneath it — stricter than the predecessor for writes and Tools, looser for reads outside the home root. The network allow-list must name real domains; the predecessor's `"*"` is now rejected, so the region a shell command can reach is exhaustive rather than open. And a Tool that touches no paths, or whose path fields cannot be found, must be declared `{"fields": [], "access": "none"}` in `tools` or it is refused. The fail-closed default is what makes these differences visible: a stale config does not degrade to a prompt, it blocks.

Consequences: the guard config is rewritten for the new schema; the agent skill is `pi-sandbox-runtime`; ADR-0004's mechanism prose is updated to match. One config line is load-bearing for a reason the schema does not show: the guard canonicalizes a claim with `realpath`, but the OS fence receives the pattern `path.resolve`-normalized and unresolved, so on macOS a symlinked writable root must be named by its real path too — `/tmp` alone lets the guard's write check pass while the shell is still denied, which is why `allowWrite` names `/tmp` and `/private/tmp`. The runtime-side fix, emitting a pattern's `realpath` spelling when it exists, would retire that line. The boundary decision itself — the agent works from source, the user applies — is unchanged, because the new guard still denies the home root to reads and every host path outside `allowWrite` to writes.
